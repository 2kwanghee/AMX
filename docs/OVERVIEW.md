# AMX 전체 안내서 (사람용)

> 이 문서는 전문용어 없이 프로젝트 전체를 이해하기 위한 안내서입니다.
> 설계의 정확한 기준은 여전히 `AMX-DESIGN.md`이지만, 그 문서가 어렵게 느껴지면
> 먼저 이 문서를 읽고 나서 돌아가면 됩니다. (2026-08-09 기준, 우선순위 ①~④ 완료 시점)

---

## 1. 이 프로젝트는 무엇인가

**AMX는 여러 대의 서버에서 쓰는 Claude 계정들을 한 곳에서 관리해 주는 시스템**입니다.

상황을 그려보면 이렇습니다. Claude 유료 계정이 10개 있고, 작업 서버가 3대 있다고 합시다.
계정마다 사용량 한도가 있어서, 한 계정을 계속 쓰면 한도에 걸려 멈춥니다. 그래서:

- 어느 서버에 어느 계정을 나눠줄지 정해야 하고 (배정)
- 계정의 로그인 정보를 그 서버에 안전하게 전달해야 하고 (하달)
- 한도가 다 차면 자동으로 다른 계정으로 갈아타야 하고 (자동 전환)
- 다 쓴 계정을 회수해서 다른 서버에 다시 줄 수도 있어야 합니다 (회수/재배정)

이걸 사람이 서버마다 접속해서 손으로 하면 실수가 나고 시간이 듭니다.
AMX는 이 전체를 **중앙 서버 하나 + 각 서버에 심어둔 작은 프로그램**으로 자동화합니다.

## 2. 전체 그림 — 네 개의 구성요소

```
[관리자 브라우저]
      │  (웹 화면)
      ▼
  ams-web  ──────►  ams-server  ◄──────  ama-agent (서버마다 1개)
  (관리 화면)        (중앙 두뇌)   보안통신      │
                        │                    ▼
                    (데이터베이스)          tsamx (계정 전환기)
                                             │
                                             ▼
                                        Claude Code (실제 작업)
```

| 구성요소 | 역할 | 비유 |
|---|---|---|
| **ams-server** | 중앙 서버. 계정·서버·배정 정보를 데이터베이스에 보관하고, 각 서버에 명령을 내리고, 보고를 받는다 | 본사 관제실 |
| **ama-agent** | 각 작업 서버에 상주하는 작은 프로그램. 관제실의 명령(계정 설치·회수 등)을 실행하고, 5분마다 사용량을 보고한다 | 지점마다 있는 직원 |
| **tsamx** | 한 서버 안에서 여러 Claude 계정을 갈아끼우는 도구. 한도가 차면 다음 계정으로 전환한다 | 계정 전환 스위치 |
| **ams-web** | 관리자가 브라우저로 보는 화면. 계정 등록, 배정, 상태 확인, 경보 확인, 정책 수정 | 관제실 모니터 |

동작 예를 하나 따라가 보면:

1. 관리자가 웹 화면에서 "계정 A를 서버 1에 배정" 클릭
2. ams-server가 계정 A의 로그인 정보를 암호화해서 서버 1의 ama-agent에게 전송
3. ama-agent가 받아서 tsamx에 등록 → 그 서버의 Claude Code가 계정 A로 동작
4. 계정 A의 한도가 95%에 도달하면 tsamx가 자동으로 계정 B로 전환하고, 그 사실이 중앙에 보고됨
5. 관리자는 웹 화면에서 "서버 1이 계정 B로 전환됨"을 확인

## 3. 디렉터리 구조 — 폴더별 안내

```
AMX/
├── ams-server/     중앙 서버 (Python)
├── ama-agent/      서버 상주 프로그램 (Go)
├── ams-web/        관리자 웹 화면 (TypeScript/Next.js)
├── tsamx/          계정 전환 도구 (Python) — 오픈소스 claude-swap을 개조한 것
├── vendor/         tsamx의 원본(claude-swap) 스냅샷 — 원본과 비교할 때만 씀
├── contracts/      네 구성요소가 주고받는 "말의 약속" (통신 규격)
├── deploy/         실제 서버에 설치할 때 쓰는 스크립트 모음
├── e2e/            네 구성요소를 전부 띄워놓고 하는 종합 시험
├── tools/          일회성 실험·조사용 스크립트
└── docs/           문서 전부
```

각 폴더를 좀 더 자세히:

### ams-server/ — 중앙 서버
- `app/models.py` — 데이터베이스에 어떤 표(테이블)들이 있는지. 테넌트(고객 그룹), 계정, 서버, 배정, 경보, 청구 등
- `app/api/v1/` — 웹 화면이 호출하는 기능들. 파일 이름이 곧 기능 (accounts=계정, servers=서버, billing=청구…)
- `app/services/` — 실제 일하는 로직. `commands.py`(명령 내리기), `reconcile.py`(보고와 실제 상태 맞추기), `billing.py`(사용량 집계) 등
- `app/grpc/` — ama-agent와의 실시간 보안 통신 담당
- `alembic/` — 데이터베이스 표의 변경 이력 (0001부터 번호순. 새 기능이 표를 바꾸면 여기에 기록이 하나 늘어남)
- `tests/` — 자동 시험. 실행법은 아래 5장

### ama-agent/ — 서버 상주 프로그램
- `internal/transport/` — 중앙 서버와의 통신 연결
- `internal/command/` — 받은 명령(계정 설치·회수 등) 실행
- `internal/store/` — 받은 로그인 정보를 암호화해서 디스크에 보관
- `internal/reporter/` — 사용량·이벤트 보고 (전송 실패해도 잃어버리지 않게 디스크에 대기열 유지)
- `internal/resync/` — 계정 로그인 정보가 서버 쪽에서 갱신되면 중앙에 되돌려 보내는 기능
- `internal/tsamx/` — tsamx 도구를 대신 조작해 주는 부분

### ams-web/ — 관리자 화면
- `src/components/` — 화면 조각들: 계정 패널, 서버 패널(정책 편집·이벤트 타임라인 포함), 배정 패널, 경보 패널
- `src/app/bff/` — 브라우저와 중앙 서버 사이의 안전 중계층 (브라우저에 서버 주소·토큰을 직접 노출하지 않기 위한 장치)

### contracts/ — 통신 규격 ("말의 약속")
서로 다른 언어(Python/Go/TypeScript)로 만든 구성요소들이 대화하려면 메시지 형식을
미리 약속해야 합니다. 그 약속이 여기 있습니다.
- `proto/amx.proto` — 중앙 서버 ↔ ama-agent 사이 메시지 정의 (원본)
- `gen/` — 위 원본에서 자동 생성된 3개 언어용 코드 (직접 수정 금지)
- `openapi.yaml` — 웹 화면 ↔ 중앙 서버 사이 기능 목록 정의
- `schemas/` — 보고 메시지(사용량 보고 등)의 형식 정의

### deploy/ — 설치 스크립트
- `amx-claude` — Claude Code 실행을 감싸는 껍데기. 계정 교체 중인 순간에 실행되면 요금이 엉뚱한 계정에 찍히는 것을 막는다
- `install-runner-guard.sh` / `verify-runner-guard.sh` — 위 껍데기를 우회해서 직접 실행하지 못하게 강제하는 설치·점검 도구
- `tls/` — 통신 암호화 인증서를 만들고 검증하는 도구 (사내 배포용)

### e2e/ — 종합 시험
단위 시험(폴더별 tests/)과 달리, 중앙 서버 + 에이전트 + 웹을 실제로 다 띄워놓고
"계정 10개를 3대 서버에 나눠주고 회수까지" 같은 시나리오 전체를 검사합니다.
**새 기능을 병합할 때마다 이걸 돌리는 것이 규칙입니다** (과거에 단위 시험만 통과하고
실제 연결에서 깨진 사고가 있어서 생긴 규칙).

**기능을 만들기 전에 "어떻게 만들지"를 미리 그려본 설계 메모**입니다.
건축으로 치면 시공 전의 도면 검토서입니다. 파일 이름의 약자는 개발 단계 이름입니다:

- `p3-architecture.md` — 3단계(자동 전환 제어) 설계
- `p4-architecture.md` — 4단계(관리자 콘솔·경보) 설계
- `p5-saas-architecture.md` — 5단계(여러 고객사가 쓰는 서비스로 확장할 준비) 설계
- `f1-rbac-architecture.md` — 관리자 권한 구분(전체 관리자 vs 고객사별 관리자) 설계
- `f2-envelope-architecture.md` — 저장 데이터 이중 암호화 설계
- `recovery-architecture.md` — 장애·재시작 후 복구 설계

이 메모들은 **역사 기록**에 가깝습니다. 구현이 끝난 지금은 "왜 이런 구조가 됐지?"가
궁금할 때 찾아보는 용도이고, 현재 사양의 최종 기준은 언제나 `AMX-DESIGN.md`입니다.

## 5. 사용 방법

> **한 번에 켜기:** `bash deploy/fullstack-run.sh up all --insecure-grpc` — DB·서버(REST+gRPC)·웹을 한 번에 띄웁니다.
> 처음부터 끝까지(노트북 에이전트 연결·실계정 왕복 포함) 따라 하는 절차는 **`docs/DEV-TEST-GUIDE.md`** 에 있습니다.
>
> **주의:** 관리자 화면(ams-web)은 개발 모드(`next dev`)로 뜨지 않습니다 — 보안정책(CSP)이 `next dev`가 요구하는
> 스크립트 실행을 막아 화면이 죽습니다. 반드시 **운영 빌드**(`npm run build && npm start`)로 띄우세요. 위 스크립트는 자동으로 그렇게 합니다.

### 개발 환경에서 시험 돌리기

```sh
# 중앙 서버 시험 (도커가 필요 — 시험용 DB를 자동으로 띄웠다 지움)
cd ams-server && uv sync --extra dev && uv run pytest

# 에이전트 시험
cd ama-agent && go test ./...

# 웹 화면 시험
cd ams-web && npm install && npm test

# 종합 시험 (전 구성요소)
cd e2e && uv run pytest        # 자세한 준비물은 e2e/README.md
```

### 중앙 서버 켜기 (개발용)

```sh
cd ams-server
# 필요한 환경 변수: 데이터베이스 주소, 암호화 키, 관리자 토큰
# → 목록과 의미는 app/config.py 에 주석과 함께 정리되어 있음
uv run alembic upgrade head        # 데이터베이스 표 만들기/갱신
uv run python -m uvicorn app.main:create_app --factory --port 8080   # 웹 API 서버
uv run python -m app.grpc.server   # 에이전트 통신 서버
```

### 관리자 화면 켜기 (개발용)

```sh
cd ams-web
cp .env.example .env.local          # 중앙 서버 주소 등 기입
npm run build && npm start          # http://localhost:3000
# 주의: `npm run dev`(개발 모드)는 보안 정책(CSP) 때문에 화면이 동작하지 않는다.
#       반드시 위처럼 운영 빌드로 실행할 것.
```

로그인 후 대시보드에서: 계정 등록(OAuth 등록 플로우) → 서버 등록(등록 토큰 발급)
→ 배정 생성 → 서버 패널에서 상태·정책·이벤트 확인, 경보 패널에서 이상 상황 확인.

### 실제 서버에 배포하기

순서대로: ① `DEPLOYMENT-TLS.md`(통신 암호화) → ② `DEPLOYMENT-TSAMX.md`(tsamx 설치)
→ ③ `DEPLOYMENT-RUNNER.md`(Claude Code 껍데기 강제) → ④ 에이전트 등록(웹에서 등록 토큰 발급).

## 6. 지금까지 구현된 것 (단계별, 쉬운 말로)

개발은 P0~P5 여섯 단계로 진행됐고 **전부 완료**됐습니다.

| 단계 | 한 줄 설명 | 결과물 |
|---|---|---|
| **P0 약속** | 구성요소들이 주고받을 메시지 형식을 먼저 확정 | contracts/ 전체 |
| **P1 장부** | 계정·서버·배정을 기록하는 중앙 장부 + 계정을 안전하게 등록하는 절차 | 데이터베이스, 등록 API |
| **P2 전화선** | 중앙 ↔ 에이전트 사이 상시 보안 통신. 계정 전달·회수가 실제로 오감 | 통신 채널, 에이전트 저장소 |
| **P3 자동 전환** | 한도 도달 시 자동 계정 전환 + 중앙이 "장부와 실제가 다르면" 스스로 바로잡는 기능 | 전환 정책, 보고-대조 |
| **P4 관제실** | 관리자 웹 화면과 경보(계정 소진, 서버 끊김 등) | ams-web, 경보 체계 |
| **P5 확장 준비** | 여러 고객사 대응: 관리자 권한 구분, 이중 암호화, 서버 다중화, 정책 중앙화, 사용량 청구 집계 | RBAC, 암호화, billing |

그 뒤에 이어진 **안정화 작업(오늘까지)**:

- **배포 안전장치**: 계정 교체 순간의 요금 오청구 방지 강제 장치, 통신 암호화 인증서 도구
- **로그인 정보 자동 되돌림**: 서버에서 갱신된 로그인 정보가 중앙에도 자동 반영되어, 다른 서버로 옮겨줄 때 죽은 정보를 주는 일이 없음 (+공격 관점 검증 완료)
- **청구 데이터 보호**: 고객사를 지워도 미정산 청구 기록이 사라지지 않게, 정산 후 정정도 가능하게
- **실패의 가시화**: 회수 실패·명령 전달 실패가 조용히 묻히지 않고 경보로 뜨며, 관리자가 강제 재시도로 풀 수 있음
- **문서-실물 일치**: 문서에만 있고 코드와 다르던 부분들을 전수 대조해 바로잡음
